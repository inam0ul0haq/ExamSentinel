Architectural Overview (Distilled from Parts 1–4)
System topology. ExamSentinel is two binaries plus one cloud service. The server is a Flask +
SQLAlchemy REST API hosted on Railway with a Railway-managed PostgreSQL instance
attached. The client is a single Windows .exe (built with PyInstaller from a Tkinter project) that
runs on examiner / student / teacher Windows 10/11 machines and talks to the server over
HTTPS. There is no peer-to-peer communication between clients; everything goes through the
server.

finalized, score is computed for MCQs.
9. All queued incidents are flushed to the server. Session is marked 
submitted .
10. Teacher reviews the session: answers, computed score, manual grading for short-answer
questions, full incident timeline.
Threat model (summary). The student is the adversary. Attacks considered: app switching,
copy/paste, screenshots, screen recorders, helper apps (Discord, AnyDesk, TeamViewer),
inspecting answer JSON via clipboard, running the exam inside a VM with hidden tooling, alt
launching restricted apps via Win/Ctrl+Esc/Task Manager, multi-monitor cheat displays. Out of
scope: a second physical device (phone), a second human in the room, OS-level rootkits,
hardware modifications. Defense layers: pre-exam VM gates → live OS lockdown → continuous
monitoring → forensic logging → teacher review. No claim of bypass-proofness; the system raises
the cost of cheating and produces a defensible evidence trail.

Prompt for Windsurf:
Read 
docs/SECURITY_DESIGN.md Standard VM Detection section. Build
client/app/vm_detect/standard.py as a pure detection module — no UI, no logging side
effects beyond what the function returns to the caller.
Public API: a single function 
detect_standard_vm() that returns a structured result
containing: 
is_vm boolean, 
vm_type one of "vmware" / "virtualbox" / "hyperv" / "qemu" /
null, 
confidence one of "high" / "medium" / "none", 
indicators a list of structured findings
each with category, name, evidence (a short string describing the matched value), and weight
(1 for soft, 2 for strong). Confidence aggregation rule: total weight ≥ 4 OR any single weight-2
indicator → high; total weight 1–3 → medium; 0 → none. is_vm is true for medium or high.
Detector implementations as separate modules under
client/app/vm_detect/standard_detectors/ : one module per detection method, each
exposing a function returning a list of indicators (possibly empty).
Process detector: uses psutil.process_iter to scan running process names against a known set
— vmtoolsd.exe, vmwaretray.exe, vmwareuser.exe, VBoxService.exe, VBoxTray.exe,
prl_tools.exe, qemu-ga.exe — case-insensitive match on the process executable basename.
Each match is a weight-2 indicator with vm_type implied by the process.
WMI hardware fingerprint detector: uses the 
wmi library to query Win32_ComputerSystem
(Manufacturer, Model), Win32_BaseBoard (Manufacturer, Product), Win32_BIOS
(Manufacturer, SMBIOSBIOSVersion), Win32_VideoController (Name). Match substrings
(case-insensitive) for VMware ("VMware", "VMW"), VirtualBox ("VirtualBox", "VBox",
"Oracle Corporation" + "VirtualBox"), Hyper-V ("Microsoft Corporation" + "Virtual
Machine", "Hyper-V"), QEMU ("QEMU"). Each match is a weight-2 indicator (BIOS-level
matches) or weight-1 (video controller, sometimes innocuous).
MAC address / OUI detector: enumerate active network adapters via WMI
Win32_NetworkAdapter where PhysicalAdapter is true, get MACAddress, normalize to the
first three octets, and match against known OUI ranges: 00:05:69, 00:0C:29, 00:1C:14,
00:50:56 → VMware (weight 2); 08:00:27, 0A:00:27 → VirtualBox (weight 2); 00:15:5D →
Hyper-V (weight 2); 52:54:00 → QEMU (weight 2). Skip adapters that have no MAC.
Registry artifact detector: uses 
winreg (stdlib) to probe presence of well-known guest-tools
registry keys — HKLM\SOFTWARE\VMware, Inc.\VMware Tools (VMware, weight 2);
HKLM\SOFTWARE\Oracle\VirtualBox Guest Additions (VirtualBox, weight 2);
HKLM\SOFTWARE\Microsoft\Virtual Machine\Guest\Parameters (Hyper-V, weight 2);
HKLM\HARDWARE\DESCRIPTION\System\BIOS where SystemManufacturer or
SystemProductName contains the same vendor strings (weight 2). Each present key is one
indicator.
Combine all detector outputs, compute confidence, derive vm_type as the most-cited type
across indicators (ties broken by weight then alphabetical). Return the structured verdict.
Resilience: every detector wraps its low-level calls in try/except — a single failing detector
must not crash the whole detection. Log to a per-module 
logging.getLogger at debug level.
Detectors that require admin (none of the above strictly do, but WMI can be flaky in
restricted environments) degrade gracefully.
Add a small CLI in 
client/app/vm_detect/__main__.py : 
python -m
client.app.vm_detect standard runs the detector and pretty-prints the verdict. This is the
dev tool the human uses to test on real hardware vs a VirtualBox guest.
Cross-version Windows compatibility: target Windows 10 and 11 only. Use APIs available on
both. Where Windows 10 lacks something, prefer the Windows 10-compatible alternative.
Commit as "security(vm): standard VM detection module".
Definition of Done: Running the CLI on bare metal returns a verdict with confidence "none".
Running it inside a default VirtualBox guest returns is_vm=true, vm_type="virtualbox",
confidence="high", with multiple indicators across processes, WMI, MAC, registry. Same in a

Detectors (each in its own module):
CPUID hypervisor-present bit detector: use ctypes to invoke the CPUID instruction at leaf 1
and inspect ECX bit 31. The cleanest portable approach inside Python on Windows is to
allocate a small piece of executable memory via VirtualAlloc with
PAGE_EXECUTE_READWRITE, write a short instruction stub that performs CPUID and
stores the result, cast to a function pointer with ctypes, and call it. Implement this carefully
with proper memory cleanup. If the bit is set, emit a weight-2 indicator "cpuid_hv_bit_set"
(vm_type unknown — set later by vendor string).
CPUID hypervisor vendor string detector: same VirtualAlloc trick at leaf 0x40000000, read
the vendor string in EBX/ECX/EDX (12 ASCII chars). Match against known strings:
"VMwareVMware" → vmware (weight 2); "VBoxVBoxVBox" → virtualbox (weight 2);
"Microsoft Hv" → hyperv (weight 2); "KVMKVMKVM\0\0\0" → kvm (weight 2);
"TCGTCGTCGTCG" → qemu (weight 2); "XenVMMXenVMM" → xen (weight 2); anything
else nonzero → unknown_hypervisor (weight 1).
RDTSC timing detector: invoke RDTSC twice around a CPUID instruction (which traps on
most hypervisors). Run several hundred iterations, take the median delta. Compare against a
calibrated threshold (the median delta on bare metal is typically under 100 cycles for that
loop body; under hypervisor it's commonly 1000+). Use a conservative threshold of 500
cycles to avoid false positives. If exceeded, emit weight-1 indicator (timing alone is noisy, so
weight 1). Populate 
timing_latency_ms of the resulting indicator with the measured median
converted to milliseconds.
Sleep skew detector: spawn a thread that calls Sleep for a known duration via ctypes Sleep,
measures wallclock delta versus a tight QueryPerformanceCounter loop, and looks for skew
patterns characteristic of hypervisor scheduling (large positive skew). Soft signal — weight 1.
False-positive prone on busy hosts; document this in code comments.
Driver enumeration detector: enumerate loaded kernel drivers via WMI
Win32_SystemDriver and look for known hypervisor-tools drivers that survive guest-tool
uninstall (vmci, vmmemctl, vboxguest, vboxsf, vboxvideo, hyperv_vsmb, etc.). Each match
weight 2.
Deep registry artifact detector: probe registry keys that survive normal cleanup —
HKLM\HARDWARE\DESCRIPTION\System SystemBiosVersion / VideoBiosVersion,
HKLM\SYSTEM\ControlSet001\Services where service names contain hypervisor strings.
Strict substring matches for vendor strings. Weight 1 (these are weaker, and modern stealth
VMs do clean some of them).
Thermal sensor anomaly detector: WMI MSAcpi_ThermalZoneTemperature query. Real
machines return varying values across multiple polls; many hypervisors return constant
"junk" values (or no thermal zone at all). Take three samples 200ms apart. If thermal zone is
missing entirely, emit weight-1 indicator. If three samples are exactly equal AND fall within a
known stub range (e.g., exactly 273.1 K = 0 C, or 300.0 K), emit weight-1 indicator. Populate
cpu_thermal_value of the indicator with the observed reading converted to Celsius.
Combine all detector outputs, compute confidence using the standard rule. Resilience: same
as Part 19 — every detector wraps in try/except, a failing detector emits no indicators (not a
crash). Detectors that require admin (none strictly do) degrade gracefully.
Pure detection — no UI, no logging side effects.
Add to the CLI: 
python -m client.app.vm_detect stealth runs stealth and pretty-prints.
python -m client.app.vm_detect both runs both and pretty-prints both verdicts side by
side.
Cross-version Windows compatibility: ensure CPUID/RDTSC stubs use byte sequences that
work on x86_64 Windows 10 and 11. Document in code comments that this module assumes
x64 — refuse to run on x86 (rare on Windows 11 anyway) by checking 
platform.machine()
early.

Likely examiner questions and prepared answers:
"Can this be bypassed?" — Yes, any software-only solution can be bypassed by a
determined adversary with hardware access; we raise the cost and produce evidence;
defense in depth not impenetrable.
"Why no Windows 7 / Linux support?" — Out of scope; security engine relies on
Windows 10/11 APIs; pywin32 calls are not portable; supporting other platforms would
require redesigning the lockdown layer (e.g., X11 vs Wayland on Linux behaves
differently).
"Why software-only and not hardware proctoring (e.g., webcam stream)?" — We
considered it; webcam proctoring requires a remote proctor or a separate AI pipeline,
both out of scope and ethically heavier (privacy implications); incident-log approach is
reviewable, auditable, and doesn't surveil the student's room.
"What's the research contribution?" — The stealth-VM detection layer combining
CPUID, RDTSC timing, sleep skew, deep registry artifacts, and thermal-zone heuristics
catches hardened VMs that survive standard detection; the offline-queued incident
pipeline guarantees evidence delivery despite intermittent connectivity; the joined
table-inheritance domain model cleanly accommodates role-specific fields without
polluting the User table.
"Why Railway not AWS/GCP/Azure?" — Cost ($5/month vs $5+ for the smallest cloud
VPS plus management overhead), zero-ops Postgres, GitHub-driven deploys, sufficient
for FYP demo scale.
"What's the database schema?" — Refer to ER diagram in 
docs/ARCHITECTURE.md ; ten
core entities, joined-table inheritance for User → Student/Teacher, junction table for
course enrollments.
